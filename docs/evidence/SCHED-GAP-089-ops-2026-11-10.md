## 4. Why the obvious fix is still not this lane's call

The blocker has two legs, both still true today:

1. **No liveness handshake.** Staleness is an inactivity heuristic. A gateway
   session can be idle for hours and still live, so an automated write pass
   can close rows the agent still considers open.
2. **The database is the agent's, not the scheduler's.** state.db is the live
   Hermes process's WAL database. A scheduled cross-process bulk UPDATE from a
   second daemon is a policy decision about the agent's own system of record,
   made while billing/usage surfaces read those rows.

A 190,476-row bulk write is also not "bounded and reversible": `ended_at` and
`end_reason='reaped'` would be stamped on a fifth of the store's session
history in one shot, during a host that is at 88% disk with a 6h backup cycle
running. Reversing it means un-stamping by hand.

## 5. The decision the owner actually has to make

- **(a) Accept the heuristic.** Authorize a schedule (e.g. daily, dry-run
  default preserved, `--reap-sessions-apply` after a clean dry-run). Buys back
  the row growth; accepts the small risk of closing an idle-but-live session.
- **(b) Fund the handshake.** Gateway reports last-seen, or the agent exposes a
  close/session-state API. Then wiring is mechanical — the seam is ready.
- **(c) Neither.** Then the 45.7 GiB of backup headroom is the clock, and the
  88%-full root is the real risk.
